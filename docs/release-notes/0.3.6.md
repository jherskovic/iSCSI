A stalled target could wedge the whole Mac. It cannot any more.

After a large soak against a real target, the volume stopped answering and
took the machine with it: Finder, Time Machine, `diskarbitrationd`, Spotlight
and anything else that touches the mount table all stuck in uninterruptible
wait behind the disk image, none of them killable, for eight hours. Ejecting
did nothing, because ejecting also touches the mount table.

Three separate faults had to line up, and all three are fixed.

**The keepalive could not notice.** Sending to a peer that has stopped reading
its socket parks forever inside Network.framework, and that send could not be
interrupted. The NOP keepalive sends the same way — so it was stuck in exactly
the same place as the I/O it was supposed to be watching. It could never miss a
ping, never declare the connection dead, and never start recovery. Eight hours
produced not one recovery event, because the mechanism for noticing was itself
blocked.

**The timeout could not fire.** The deadline that bounds every SCSI command
raced the work against a timer inside a task group. A task group cannot return
until every child finishes, and cancelling an operation that is parked on a
continuation does nothing at all — so the deadline expired, changed nothing,
and waited alongside the work it was meant to abandon.

**A dead volume was retried forever.** Each read cost a full 30-second timeout
before failing with an error the layers above treat as temporary, so they tried
again. Three unanswered calls in a row now mark the volume dead and every
request after that fails immediately, which is what lets the filesystem give up
in seconds instead of never. A SCSI error still does not count — a bad block
must not be able to condemn a healthy volume.

Six new tests cover this, including one that stalls a send the way a real
target does. The existing suite could not have caught it: the in-memory
transport used by tests never blocks on send, and the simulator stalls replies
rather than sends.
